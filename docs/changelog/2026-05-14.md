# 변경 이력 — 2026-05-14

## 현재 시스템 구조

```
PDF 업로드 → SHA-256 해시 중복 체크 (비관적 락, 짧은 트랜잭션)
         → 텍스트 추출 (PDFBox) — 동기, ~1-2초
         → 즉시 PROCESSING 반환 (HTTP 응답 종료)
         ↓ [백그라운드 스레드 — pdfTaskExecutor]
         → 청크 분할 (문단 경계 기준, 최대 2500자, 300자 오버랩)
         → 청크 병렬 번역 (vllm.translation-concurrency=10, flatMapSequential)
           EN→EXAONE 3.5 32B AWQ :8001 / ZH·JA→Qwen 14B :8000
         → 번역본 합치기
         → 번역본을 5000자 청크로 재분할
         → 소요약(Map) 병렬 생성 (vllm.summary-concurrency=4)
         → 소요약 합산 4000자 → 최종 요약(Reduce, Qwen 14B :8000)
         → DB 저장 (PostgreSQL) — status DONE / FAILED
```

인프라:
- vLLM EXAONE 3.5 32B AWQ: DGX Spark GB10 (EN 번역 전용)
- vLLM Qwen 2.5 14B: DGX Spark GB10 (ZH/JA 번역, 소요약, 통합 요약)
- DB: PostgreSQL (로컬 Docker)
- 비동기 스레드풀: corePoolSize=2, maxPoolSize=4, queue=20 (pdf-async-*)

## 작업 이력

### [아키텍처] @Async 비동기 처리 도입

- **이유**: `PdfService.upload()`가 번역·요약이 끝날 때까지 HTTP 요청을 수십 분 블로킹. HTTP 타임아웃 위험 및 UX 불량. `recoverStaleProcessing()`이 존재하는 근본 원인이기도 함.
- **변경 파일**:
  - `PdfSummaryApplication.kt` — `@EnableAsync` 추가
  - `config/AsyncConfig.kt` (신규) — `pdfTaskExecutor` ThreadPoolTaskExecutor (core=2, max=4, queue=20)
  - `service/PdfAsyncProcessor.kt` (신규) — `@Async("pdfTaskExecutor") processAsync(docId, sourceLang)`. 번역·소요약·최종요약·DB저장 전 파이프라인 담당. `@Async`는 같은 클래스 내 호출에 AOP 프록시가 적용되지 않아 별도 빈으로 분리.
  - `service/PdfService.kt` — `upload()`: 텍스트 추출 후 즉시 PROCESSING 반환, `asyncProcessor.processAsync()` 호출. `retry()`: PROCESSING 저장 후 즉시 반환. `translateSummarizeAndSave()` 제거 (PdfAsyncProcessor로 이동). `vllmService` 의존성 제거.
  - `controller/PageController.kt` — `index()`: `hasProcessing` 모델 속성 추가. 플래시 메시지 문구 수정.
  - `templates/index.html` — PROCESSING 문서 존재 시 5초마다 자동 갱신(location.reload). 업로드 스피너 문구 수정.
- **결과**: 업로드 후 1-2초 안에 HTTP 응답 반환. 번역·요약은 백그라운드에서 실행. UI가 5초 주기로 상태를 자동 갱신하여 DONE/FAILED 전환 확인 가능.
