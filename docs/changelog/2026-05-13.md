# 변경 이력 — 2026-05-13

## 현재 시스템 구조

```
PDF 업로드 → SHA-256 해시 중복 체크 (비관적 락, 짧은 트랜잭션)
         → 텍스트 추출 (PDFBox)
         → 청크 분할 (문단 경계 기준, 최대 2500자, 300자 오버랩)
         → 청크 병렬 번역 (vllm.translation-concurrency=4, flatMapSequential)
           EN→EXAONE 3.5 32B AWQ :8001 / ZH·JA→Qwen 14B :8000
         → 번역본 합치기
         → 번역본을 3000자 청크로 재분할
         → 소요약(Map) 병렬 생성 (vllm.summary-concurrency=2)
         → 소요약 합산 4000자 → 최종 요약(Reduce, Qwen 14B :8000)
         → DB 저장 (PostgreSQL) — status / 처리 시간 기록
```

인프라:
- vLLM EXAONE 3.5 32B AWQ: DGX Spark GB10 (EN 번역 전용)
- vLLM Qwen 2.5 14B: DGX Spark GB10 (ZH/JA 번역, 소요약, 통합 요약)
- DB: PostgreSQL (로컬 Docker)

## 작업 이력

### [버그] @Lob 어노테이션으로 인한 PostgreSQL LOB 에러
- **이유**: `PdfDocument.kt` 텍스트 필드에 `@Lob` 붙어 PostgreSQL이 Large Object(OID)로 처리. LOB는 auto-commit mode에서 읽을 수 없어 업로드 시 500 에러 발생.
- **에러**: `PSQLException: Large Objects may not be used in auto-commit mode`
- **변경 파일**: `PdfDocument.kt` — `@Lob` 3개 제거. `columnDefinition = "TEXT"` 로 타입이 이미 명시되어 있으므로 `@Lob` 불필요.
- **결과**: 업로드 정상 동작

### [개선] 요약 타이밍 로그 추가
- **이유**: 번역은 청크별 로그가 있었지만 요약 단계는 모델명/입력 크기 로그 없었음
- **변경 파일**: `VllmService.kt` — `summarizeAsync()` 시작 시 모델명/입력 크기 로그 추가

### [기능] ProcessingStatus 상태 관리 컬럼 추가
- **이유**: 업로드 처리 중 상태 추적 불가. 실패/완료 여부를 DB에서 확인할 수 없었음.
- **변경 파일**:
  - `ProcessingStatus.kt` (신규) — PENDING / PROCESSING / DONE / FAILED / CACHED enum
  - `PdfDocument.kt` — status, startedAt, completedAt, processingTimeSec 컬럼 추가. 가변 필드 `val` → `var` 변경.
  - `PdfService.kt` — 업로드 시작 시 PROCESSING 저장, 완료 시 DONE, 예외 시 FAILED 전이
  - `PdfUploadResponse.kt` — status 타입 `String` → `ProcessingStatus` enum 변경
  - `application.yaml` — `ddl-auto: validate` → `update` (새 컬럼 자동 추가)
  - `schema.sql` — status / started_at / completed_at / processing_time_sec 컬럼 추가 (IF NOT EXISTS)
- **결과**: 처리 중·완료·실패 상태를 DB에서 추적 가능

### [기능] Stale Processing 자동 복구
- **이유**: 앱 재시작이나 예외 누락으로 PROCESSING 상태가 영구히 남을 수 있음
- **변경 파일**:
  - `PdfDocumentRepository.kt` — `findByStatusAndStartedAtBefore` 쿼리 메서드 추가
  - `PdfSummaryApplication.kt` — `@EnableScheduling` 추가
  - `PdfService.kt` — `@Scheduled(fixedDelay=60_000)` `recoverStaleProcessing()` 추가. startedAt이 10분 이상 지난 PROCESSING 레코드를 FAILED로 전환 후 log.warn 기록.
- **결과**: 1분마다 체크, 10분 초과 PROCESSING → 자동 FAILED 전환

### [기능] 처리 시간 API 응답에 노출
- **이유**: processingTimeSec / completedAt이 DB에는 저장되나 API 응답에 없었음
- **변경 파일**: `PdfSummaryResponse.kt` — `completedAt`, `processingTimeSec`, `status` 필드 추가 및 `from()` 매핑 추가

### [기능] 중복 파일 체크 동시성 안전 처리
- **이유**: `findByFileHash` 후 `save` 사이에 동일 파일 동시 요청 시 중복 저장 가능
- **변경 파일**:
  - `PdfDocumentRepository.kt` — `findByFileHashForUpdate` 추가 (`@Lock(PESSIMISTIC_WRITE)`, lock timeout 3초)
  - `PdfService.kt` — `TransactionTemplate`으로 lock 체크 + 초기 저장을 짧은 트랜잭션으로 분리. `DataAccessException` 캐치 후 사용자 메시지 반환. 번역/요약은 트랜잭션 밖에서 실행 (커넥션 풀 고갈 방지).
- **결과**: 동일 파일 동시 업로드 시 한 건만 처리, 나머지 409 유사 메시지 반환

### [UI] FAILED 상태 표시 및 재시도 기능
- **이유**: 처리 실패한 문서를 UI에서 구분할 수 없었고 재시도 수단이 없었음
- **변경 파일**:
  - `index.html` — 상태 컬럼 추가 (색상 배지: done/failed/processing/cached/pending). FAILED 행 배경 연빨강. FAILED 레코드에 재시도 버튼 추가 (form POST).
  - `detail.html` — FAILED 경고 배너, 처리 정보 카드(status/completedAt/processingTimeSec) 추가. DONE/CACHED 상태에만 요약·번역 카드 렌더링.
  - `PdfController.kt` — `POST /api/pdf/retry/{id}` 추가
  - `PageController.kt` — `POST /retry/{id}` → `redirect:/detail/{id}` 추가
  - `PdfService.kt` — `retry(id)` 구현: FAILED 상태 확인 → PROCESSING 재전환 → `translateSummarizeAndSave()` 재실행
- **결과**: UI에서 실패 상태 확인 및 원클릭 재처리 가능

### [성능] Map-Reduce 요약 도입
- **이유**: 번역본이 6000자를 넘을 때 앞·중간·뒤 일부만 요약 입력으로 사용해 후반부 내용이 누락됐음
- **변경 파일**:
  - `VllmProperties.kt` — `summaryChunkSize: Int = 3000` 추가
  - `application.yaml` — `vllm.summary-chunk-size: 3000` 추가
  - `VllmService.kt` — `chunkSummarizeAsync()` 추가 (3문장 소요약, maxTokens=300)
  - `PdfService.kt` — 요약 로직 교체: 번역본 3000자 청크 분할 → 소요약 병렬 생성 → 합산 4000자 → `summarizeAsync()` 최종 요약
- **결과**: 번역본 전체 내용 반영. 긴 문서 후반부 내용 누락 방지.

### [품질] 번역 청크 간 컨텍스트 주입 (prevContext)
- **이유**: 각 청크가 독립적으로 번역되어 청크 경계에서 문체·용어 불일치 발생
- **변경 파일**:
  - `VllmService.kt` — `translateAsync(chunk, sourceLang, prevContext = "")` 시그니처 변경. prevContext 있을 때 시스템 프롬프트에 이전 단락 번역 결과 주입.
  - `PdfService.kt` — `Flux.flatMapSequential` 블록 → 순차 `for` 루프로 교체. 각 청크 번역 완료 후 `prevContext = result.takeLast(200)` 갱신.
- **결과**: 청크 경계에서 문체·전문용어 일관성 향상. 첫 청크는 prevContext 없이 시작.
- **참고**: prevContext는 이전 결과에 의존하므로 병렬 실행 불가. 번역은 순차 실행으로 전환됨.

### [품질] 번역·요약 프롬프트 전면 개선
- **이유**: 프롬프트가 범용적이어서 논문/특허/계약서/기술문서 특성을 반영하지 못했음
- **변경 파일**: `VllmService.kt`
  - `callTranslate()`: 전문 번역가 페르소나 + 문서 유형 명시. 전문용어 첫 등장 영문 병기. `~다/~이다` 체 통일. 수식·단위·모델명 원문 유지. 청크 경계 자연스럽게 처리. retry 프롬프트도 동일 규칙 적용.
  - `chunkSummarizeAsync()`: 3문장 고정 구조 (핵심 주장 1개 + 근거 2개). 수치·고유명사 필수 포함. 불필요한 접속어·부연 제거.
  - `summarizeAsync()`: 문서 유형 5종 (학술 논문 / 특허 / 계약서 / 기술문서 / 보고서) 섹션 구조를 프롬프트에 직접 명시. 논문 결과 섹션 수치 3개 이상 강제. 전문용어 영문 병기. bullet보다 `###` 헤더 우선. `maxTokens` 1200 → 1500.
- **결과**: 문서 유형별 구조화된 요약 품질 향상. 번역 문체 일관성 개선.

### [설정] 미사용 설정값 정리 및 소요약 concurrency 외부 설정화
- **이유**: `translationConcurrency`가 번역 순차화로 미사용 상태. 소요약 concurrency가 `2`로 하드코딩되어 있었음.
- **변경 파일**:
  - `VllmProperties.kt` — `translationConcurrency` 제거, `summaryConcurrency: Int = 2` 추가
  - `application.yaml` — `translation-concurrency` 제거, `summary-concurrency: 2` 추가
  - `PdfService.kt` — 소요약 `flatMapSequential` 인자 하드코딩 `2` → `vllmProperties.summaryConcurrency`
- **결과**: 설정 파일만 수정해 소요약 병렬도 조정 가능

### [롤백] prevContext 제거 → 병렬 번역 복구
- **이유**: prevContext 주입으로 인해 번역이 순차 for 루프로 전환되어 처리 시간이 5분 → 40분으로 급증
- **변경 파일**:
  - `VllmService.kt` — `translateAsync()` prevContext 파라미터 제거. `callTranslate()` prevContext 관련 코드 전부 제거. 나머지 프롬프트 개선사항(문체 통일, 영문 병기 등)은 유지.
  - `PdfService.kt` — 순차 for 루프 제거. `Flux.flatMapSequential(concurrency=translationConcurrency)` 복구.
  - `VllmProperties.kt` — `translationConcurrency: Int = 4` 재추가.
  - `application.yaml` — `vllm.translation-concurrency: 4` 재추가.
- **결과**: 병렬 번역 복구. 처리 시간 정상화.

### [설정] Stale timeout 외부 설정화
- **이유**: PROCESSING 레코드 복구 기준 시간(10분)이 하드코딩되어 있어 조정 불가. 병렬 번역 복구 이후에도 긴 문서 처리가 30분 이상 걸릴 수 있음.
- **변경 파일**:
  - `VllmProperties.kt` — `staleTimeoutMinutes: Int = 30` 추가
  - `application.yaml` — `vllm.stale-timeout-minutes: 30` 추가
  - `PdfService.kt` — `recoverStaleProcessing()` 하드코딩 10 → `vllmProperties.staleTimeoutMinutes`
- **결과**: 설정 파일에서 stale 판정 기준 시간 조정 가능. 기본값 30분으로 상향.
